# Web 控制台拆分方案

## 结论

当前控制台的主要问题不是 URL 名字本身，而是一个请求同时承担了所有页面的数据查询、HTML 渲染和前端脚本交付。建议采用**多页 Flask + 共享基础模板 + 页面内按需 API 加载**，先不引入 React/Vue，也不拆成多个服务。这个方案改动可分批上线，能以较低成本同时缩短首屏时间并缩小故障影响范围。

## 现状与问题定位

### 1. 单个后端请求做了过多工作

`GET /safety/abnormal-wicks` 当前同时读取异常插针、18 条评分规则、市场过滤、模拟盘、实盘、持仓保护与配置数据。即使用户只打开一个隐藏 tab，服务端仍会执行其他 tab 的查询。当前 route 约 386 行，包含约 80 次 `load_module(...)` 调用；这些查询大多串行执行，延迟会累加。

现有 `_safe_page_module` 已经能把不少模块异常降级为空数据，这一点应保留。但配置初始化、部分配置读取、上下文组装和最终模板渲染仍位于模块级隔离之外；其中任一步骤失败，整个请求依然会失败。

### 2. 单个模板形成前端故障域

`templates/abnormal_wicks.html` 目前约 5,662 行、391 KB，包含 9 个顶层 section 和约 28 个 `fetch(...)` 调用。隐藏 tab 的 HTML、样式和脚本仍要下载、解析并初始化。一个模板语法错误或共享 `<script>` 中的 JavaScript 语法错误，也可能让所有 tab 同时不可用。

### 3. URL 与业务边界不匹配

评分、市场、模拟盘、实盘和配置都挂在 `/safety/abnormal-wicks` 下，并通过 `active_tab` 切换。这使刷新、收藏、权限控制、监控和故障定位都只能看到同一个 endpoint，无法判断究竟是哪块功能慢或失败。

## 推荐目标结构

建议第一阶段拆成下列 5 个页面，导航仍保持现有顺序和视觉风格：

| 页面 | 建议 URL | 只加载的数据 |
| --- | --- | --- |
| 市场安全 | `/safety/abnormal-wicks` | 异常插针、BTC K 线、市场过滤 |
| 评分与开仓 | `/strategy/scoring` | 18 条规则、总分、趋势、可开仓与冷却 |
| 模拟盘 | `/trading/simulation` | 模拟持仓、交易记录、权益与保护模块 |
| 实盘 | `/trading/live` | 实盘持仓、交易记录、权益与保护模块 |
| 系统配置 | `/settings` | 功能开关和各模块配置 |

`/` 可改为轻量导航/健康概览页。已有 `/safety/abnormal-wicks?active_tab=...` 链接在过渡期应做 302 跳转并保留其他查询参数，避免旧书签立刻失效。

## 实现方式

### A. 先拆模板和 route，不换技术栈

1. 提取 `templates/base.html`，只放页面骨架、全局导航、基础样式和全局错误提示。
2. 每个业务页使用独立模板，并把只在该页使用的 JavaScript 放到独立静态文件，例如 `static/js/simulation.js`。
3. 将当前 route 的数据准备逻辑按业务域提取为纯 context loader，例如 `load_scoring_context()`、`load_simulation_context()`；每个 route 只调用自己的 loader。
4. 保留现有 JSON API。表格的首次数据可以继续 SSR；图表、成交订单、BTC K 线及高频模块详情继续或改为用户进入页面后再请求。

这样不需要前端框架、状态管理或新构建工具，测试方式也能沿用 Flask test client 和现有模板测试。

### B. 页面内采用“区块独立失败”

每个 context loader 继续复用 `_safe_page_module`，并让页面以卡片为单位显示错误，而不是返回整页 500。前端请求统一使用一个 `fetchJson` helper，包含：

- `AbortController` 超时（建议读取类请求 8 秒）；
- 非 2xx 和非 JSON 响应的统一处理；
- 单卡片错误态和“重试”按钮；
- 请求中的 loading/skeleton 状态；
- 防止重复点击触发并发请求。

关键原则是：模拟盘失败不影响实盘，某个止盈模块失败不影响同一页面的持仓概览。

### C. 只对只读数据做短缓存

对最新评分、市场摘要和历史记录等只读查询可加入 5–15 秒的进程内 TTL 缓存；所有配置写入后主动失效对应缓存。不要缓存余额、提交订单结果、功能开关写操作，也不要把缓存作为一致性来源。

缓存是第二优先级。应先按页面减少无关查询，再通过耗时数据决定是否缓存，避免用缓存掩盖慢 SQL。

### D. 增加最低成本的可观测性

为每个页面和 API 记录 endpoint、状态码、总耗时；为 context loader 记录模块名和耗时，超过 500 ms 时输出 warning。响应可增加 `Server-Timing`，便于直接在浏览器 Network 面板定位慢模块。

## 建议实施顺序

### 第 1 批：低风险、高收益

- 建立 `base.html` 和共享静态资源。
- 先拆 `/settings`，它与行情展示耦合最低。
- 再拆 `/trading/live` 与 `/trading/simulation`，立即隔离两个最重要的故障域。
- 原 URL 的 `active_tab` 兼容跳转。
- 为新 route 添加“只调用本页 loader”的单元测试，以及某个 loader 抛错时页面仍返回 200 的测试。

### 第 2 批：改善重页面体验

- 拆评分与市场页。
- 将 BTC、趋势图、成交记录、高频模块详情改为按需请求。
- 拆分页面 JavaScript，并增加统一请求错误组件。

### 第 3 批：基于数据优化

- 加入 loader 耗时日志和 `Server-Timing`。
- 针对实际慢查询补索引或 5–15 秒 TTL 缓存。
- 如果以后团队和流量明显增长，再考虑 Flask Blueprint；目前没有必要上微服务或完整 SPA。

## 对现有 Docker 部署的影响

### 当前这份变更

当前提交只新增方案文档，没有修改 Python、模板、镜像入口、端口、环境变量或数据库结构。因此现在服务器上的启动命令无需改变，也不需要仅为了这份文档重新构建或重启容器。

### 后续实施拆页时

拆页仍运行同一个 Flask/Gunicorn Web 进程，容器入口参数继续使用 `web`，监听端口继续是容器内的 `5000`。数据和日志仍分别位于 `/app/data` 与 `/app/logs`，所以现有 volume 挂载和 `--env-file /root/.env` 都可以保持不变。实施后仍可使用：

```bash
docker run -d \
  --name trade-web \
  --user "$(id -u):$(id -g)" \
  -v /root/trade/data:/app/data \
  -v /root/trade/logs:/app/logs \
  -p 5000:5000 \
  --env-file /root/.env \
  --restart=always \
  trading-sys-demo web
```

需要注意以下几点：

1. 代码和模板是在构建镜像时复制进去的，因此实施拆页后必须重新执行 `docker build -t trading-sys-demo .`，仅重启旧容器不会得到新页面。
2. 如果按本方案新增 `static/js/...`，必须同时在 `Dockerfile` 中加入 `COPY static ./static`；当前镜像只复制 Python 文件、评分配置、`templates` 和入口脚本。
3. 新旧容器不能同时使用 `--name trade-web` 或同时绑定宿主机 `5000` 端口。简单更新时应先删除旧容器再用原命令启动；需要低停机更新时，可让候选容器使用不同名称和临时端口验证后再切换反向代理。
4. 页面拆分不迁移、不重建数据库，也不会改变 `/app/data` 的挂载位置。回滚到旧镜像时仍读取同一批数据库文件。
5. 应继续保留 `/` 的轻量响应，因为现有 Compose 健康检查访问该地址。拆页时不要把 `/` 改成依赖全部业务数据库查询的聚合页，否则会重新扩大健康检查的故障域。

推荐的普通更新流程是：

```bash
cd /root/trade
docker build -t trading-sys-demo .
docker rm -f trade-web
# 再执行上面的 docker run 命令
curl -fsS http://127.0.0.1:5000/ >/dev/null
```

如果服务器还同时运行 worker，更新 `trade-web` 不会自动更新 worker 容器。纯 Web 拆页不要求重启 worker；若同一次发布还修改了 worker 使用的 Python 业务代码，则应使用同一新镜像分别重建两个容器。

## 不建议的方案

- **只修改 URL 或用前端隐藏 tab：** 后端仍执行全量查询，性能和故障域不变。
- **用 iframe 包装现有大页面：** 无法减少服务端查询，还会增加导航、样式和认证复杂度。
- **立刻重写成 React/Vue SPA：** 需要重新处理路由、构建、状态和测试，投入大，但后端全量 context 的根因仍需单独解决。
- **立刻拆微服务：** 当前共享 SQLite 与单体业务对象会使服务拆分成本远高于收益，并引入部署和一致性问题。
- **把所有数据一次改成前端并发请求：** 虽可能改善首屏，但会瞬间放大 SQLite 并发读取；应按页面和可见区块按需发起，并设置并发与超时边界。

## 验收指标

建议上线前在相同数据副本上记录基线，上线后以以下条件验收：

1. 每个页面的服务端查询只属于当前业务域；路由测试可通过 mock 明确验证无跨域 loader 被调用。
2. 非缓存情况下，各页面 p95 TTFB 相比原页面至少下降 50%，并分别记录而不是只看总平均值。
3. 初始 HTML（未压缩）每页控制在 150 KB 以下；非当前页脚本不会下载。
4. 任一非关键模块查询失败时，当前页仍返回 200 并展示该模块错误卡片；其他页面完全不受影响。
5. 实盘和模拟盘的查询、错误日志和报警可通过 endpoint 清楚区分。
6. 旧链接在过渡期能跳转到对应新页面，所有写操作 API 的行为保持不变。

## 成本与收益判断

最高性价比的切入点是“**拆成 5 个 Flask 页面，按页面加载数据**”。它复用当前后端、Jinja、API 和测试体系，不要求新基础设施；同时直接消除隐藏 tab 的无效查询和巨型模板的共享故障域。短缓存和 SQL 优化应建立在拆页后的耗时数据上，而不是作为第一步。
